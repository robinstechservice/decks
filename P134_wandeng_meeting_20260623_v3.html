一、萬登保代財務交接與稅務議題

主要發言者：佑璇、Eason、Jimmy、Evin、Matt

會議首先由財務佑璇發起，針對羅賓斯科技接手萬登保代後的帳務整合問題進行討論。佑璇指出，過去萬登的帳務主要由凱樂會計師事務所與 Eason 處理，為符合查帳規定，她需要與 Eason 進行正式交接。交接內容包含萬登的收入明細（如保險公司的對帳單「報表90」）以及支出憑證，特別是付給個人的「勞報單」。

佑璇強調，1-5 月的勞報單需向萬登前期的經手人靖宇索取，以確保年底的各類所得扣繳申報無誤。她詳細解釋了扣繳的重要性：若未對超過兩萬元的個人佣金進行預扣繳，未來該收款人可反向檢舉公司，導致公司需自行吸收罰款與稅金，存在財務風險。

接著，會議深入討論了公司成員的薪資與獎金發放方式。針對 Jimmy 同時具備萬登員工與羅賓斯科技獎金領取者的雙重身份，佑璇澄清其保險佣金獎金應歸類為「薪資所得」，而非可扣除較高成本率的「執行業務所得」，與過去的處理方式一致。而對於掛在羅賓斯科技底下的員工（如 Matt），若協助萬登業務產生獎金，金流應為：萬登支付服務費給羅賓斯科技，再由科技公司以「執行業務所得」名義發放給 Matt，這樣才合規。

最後，佑璇提到萬登的發票購票證因公司地址變更需更新，但公司大小章目前因辦理名稱變更（已確認更名為「未來保險代理有限公司」）而被代辦的里派會計師事務所保管。會議決議，待名稱變更程序完成後，由佑璇立即取回大小章，並與負責人 Jimmy 親自前往國稅局辦理新的購票證，同時處理後續的銀行帳戶印鑑變更等行政事宜。

三、核心專案：遠見保經 OCR 系統上線規劃

主要發言者：Evin、Leon、Eason、Ray、Jimmy

會議的核心議程之一是規劃將羅賓斯科技的 OCR（光學字元辨識）系統導入給客戶「遠見保經」的詳細時程。Evin 擔任總指揮，制定了為期兩週的衝刺計畫，目標在 7 月 13 日正式上線。

專案分工明確：由 Eason 擔任此專案的主要對外窗口與 PM，負責與遠見的總經理對接，確認他們系統所需的 Excel 產出格式、使用者與管理者名單，並在系統建置後負責製作教學文件與執行線上教育訓練。技術開發則由 Leon 負責。

會議深入探討了系統的技術規格，特別是後台管理功能與權限設計。決議 MVP (Minimum Viable Product) 版本需包含以下功能：

1. 管理員權限：為遠見保經建立一個總管理員帳號，該帳號可以新增、刪除、管理其下的所有行政人員帳號。

2. 使用量監控：總管理員可在後台查看每位行政人員（或每個單位）的 OCR 使用狀況，包含掃描次數、對應金額及操作時間紀錄，以便內部管理。

3. 資料隱私：羅賓斯科技的後台管理員無法查看遠見保經上傳的保單個資內容，僅能看到使用量數據，確保客戶資料的隱私與安全。

4. 權限劃分：為求快速上線，初期採用二層式架構。遠見的行政人員將以「部門」為單位共用一個帳號，他們只能看到自己部門（該帳號）上傳的保單資料，無法跨部門查看。總管理員則能看到所有部門的資料。此舉雖在資安追蹤上非最優解，但能最快滿足客戶需求。

Evin 設定了明確的 Deadline：6/26 完成合約簽署，7/3 完成使用者名單確認與帳號建立，7/10 前完成所有教學與問題彙整，最終於 7/13 正式上線。

四、技術瓶頸 (一)：廠牌代碼查詢功能優化

主要發言者：Leon、Evin、Jimmy、Ray

會議針對內部車險報價系統中的「廠牌代碼查詢」功能進行了深度技術檢討。問題在於，當使用者輸入車牌號碼後，系統雖能從監理站獲取車輛基本資料，但在匹配保發中心的廠牌代碼時，常因同一車款有多種型號（如豪華版、運動版）而列出多個選項，且系統自動推薦的選項準確度不足。

Leon 解釋，目前的演算法已使用廠牌、車型、年份、CC 數等資訊進行比對與評分排序。然而，Evin 質疑為何系統有時會推薦分數並非最高的選項，並指出當前 UI/UX 設計未提供足夠資訊讓使用者進行人工判斷。

Jimmy 以其理賠經驗補充，實務上報價人員主要參考「當年度」的車款資料。基於此，團隊進行了腦力激盪，提出多項優化方案：

1. 增加顯示欄位：在選項列表中，額外顯示每款車型的「出廠年份」與從 Yahoo 拍賣等外部網站爬取的「重置價格」（新車價），作為使用者判斷的依據。Leon 表示價格爬取準確率約 50%，但抓到的價格是準確的。

2. 優化排序邏輯：將排序規則調整為優先顯示與行照年份「同年份」的車款，其次是前一年的車款，依此類推。

3. 納入更多維度：考慮加入「式樣」（如轎式、休旅式，可判斷四門/五門）與「燃料種類」等監理站資料進行篩選，但 Leon 提醒這些資料在保發中心端有時不完整或不一致。

最終決議，由 Leon 著手修改系統，增加年份與價格欄位並優化排序邏輯。同時，指派 Ray 去訪談實際在第一線操作的保險人員（如陳誠），深入了解他們在面對多個選項時的「人工判斷邏輯」，將其經驗轉化為更精準的系統規則。

五、技術瓶頸 (二)：SaaS 平台開發與廠商協作挑戰

主要發言者：Ray、Evin、Leon

Ray 報告了七月份即將啟動的 SaaS 平台重構專案。此專案將與外部開發商「古感」合作，重新設計車險與旅平險的投保流程與 UI/UX。

然而，會議焦點迅速轉移至當前與古感合作開發、提供給「富易達」使用的 SaaS 平台所面臨的瓶頸。張總（富易達）昨日已反饋系統操作流程過於繁瑣，且報價功能連續兩次失敗。對此，會議確立了優先級：必須先解決並優化富易達現有的 SaaS 平台，再啟動新平台的開發。

技術問題分為兩個層面：

1. API 穩定性：報價失敗的主因是串接「泰產」的 API 不穩定。Leon 透過後台 log 確認問題根源在泰產端，非古感開發問題。這需要羅賓斯、古感、泰產三方持續溝通解決。

2. 核心架構風險：Leon 揭露一個更嚴重的問題，目前的 SaaS 平台與公司既有的保代後台，共用同一套後端核心服務 (insurance service)。這意味著任何為了 SaaS 平台所做的修改，都可能影響到既有保代系統的穩定性，風險極高。

為解決此架構問題，Leon 提出兩個方案：一是在既有服務中加入複雜的判斷邏輯，區分不同來源的請求；二是將服務徹底拆分為二，各自獨立。Evin 傾向後者，認為雖然短期開發成本較高，但長期來看更為乾淨、穩定，且有利於未來將舊系統關閉。

為此，Evin 決定當天下午 3:30 親自帶領 Leon 與古感的 PM Rocky 召開緊急會議，旨在明確劃分三方權責，並就後端服務拆分的技術方案進行最終決策。
